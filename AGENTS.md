# AGENTS.md

## Scope and architecture

This is **Daisy Nduta**'s (Nairobi-based sound designer, location recordist, and cultural producer) portfolio site: static HTML/CSS/JS, hosted on **GitHub Pages** (free tier) with a custom domain the client points at it. As of the CMS work, the site has a build step — **read "Content, the CMS, and the build" below before touching any `.html` file.**

- Content/IA source of truth for wording: `daisy-nduta-website-copy.md.pdf` in the project root (client-supplied copy doc). Treat its wording, tables, and the "Open items still needed from you" list as authoritative; do not invent facts to fill gaps it leaves open. The PDF's actual data now lives in `content/`, not embedded in HTML — see below.
- Three tiers of page, all sharing `style.css` and deferred `script.js`:
  1. **Home** (`index.html`) — no header/nav at all. A giant centered `h1.home-wordmark` ("Daisy Nduta") sits on top of an auto-rotating carousel of the same five `.entry-card` links (Sound / Curation & Production / Cultural Projects / About / Contact) — the whole journey starts from these cards, no nav needed. `.page--home` carries extra top margin so the wordmark has real breathing room below the header-less top of the page. See "Home's rotating cards" below for how the carousel itself works. **The wordmark has an editable one-line tagline underneath it (2026-09-20, client request)** — `home.json`'s `tagline` string, rendered as `.home-wordmark__tagline` right below the `h1` (only when non-empty), edited from the top of the Home Page admin form. Plain text, no accent/markup treatment.
  2. **Section pages** — `sound.html`, `curation-production.html`, `cultural-projects.html`, `about.html`, `contact.html`. These keep the persistent top-right `.site-header`/`.site-nav` (a left-hand rail nav was tried and reverted — see below). Sound has five `.section`s (Film, Theatre, Broadcast, Live, Studio, each with an `id` used as an anchor target, e.g. `sound.html#film`), each listing its credits as an `.item-grid` of `.item-card`s. Curation & Production and Cultural Projects are a single `.item-grid` each.
  3. **Item detail pages** — one HTML file per credit/project (~28 files, e.g. `mwakenya.html`, `kilele-summit.html`, `frequency-shift.html`). Each has a breadcrumb eyebrow, title, `.image-panel` (placeholder or a real `<img>` once one's uploaded), copy paragraph, a `.detail-list` of role/year/credit facts, and a `.project-navigation` (back-to-section link + prev/next within that subsection, looping).
- **Navigation history:** a left-hand fixed rail (`.site-rail`, small ~13px vertical links) replaced the top nav briefly, then was reverted back to the original top-right `.site-header`/`.site-nav` because it "wasn't looking the best." If asked to revisit nav placement, treat the current top-right layout as the known-good baseline, not the rail.
- **Kaya** and **Assimilate** are genuinely the same two projects in both Sound → Theatre and Cultural Projects (per the PDF's own cross-reference note) — they exist as a single `kaya.html`/`assimilate.html` file each (and a single content file each, under `content/sections/cultural/`), with a `.cross-listed` note pointing to the other section, rather than being duplicated. Their prev/next chain runs through Cultural Projects (frequency-shift → mau-from-nowhere → kaya → assimilate), since that's their fuller framing in the PDF; Sound → Theatre's card grid *also* shows their cards via the `alsoShowOn` content field (see below). Every other "mau from nowhere" credit (the Film music-video Producer credit, the Curation & Production listening party, and the Cultural Projects artist-management entry) is a genuinely distinct engagement with its own content file — don't merge those.
- `script.js` creates `#topographic` itself and draws one of **four genuinely different pointer-reactive animations**, chosen per page via `<body data-bg="...">` (no attribute — Home/About/Contact — falls back to `puddles`): `puddles` (a single shared water surface — a stack of horizontal lines whose displacement at every point is the *sum* of every ripple source's wave, so overlapping ripples reinforce or cancel each other rather than existing as independent circles; most sources trail the pointer), `sound` (Sound section + its item pages; a stack of flowing waveform lines that swell in amplitude near the pointer), `curation` (Curation & Production + its items; a large orbital/planetary system — 6 elliptical orbit rings extending well past the viewport, a central body, and planets that speed up, glow, and leave a short trailing echo along their orbit as the pointer passes near them), `cultural` (Cultural Projects + its items, including the shared Kaya/Assimilate pages; a drifting node network where the pointer itself joins as a node). This is the confirmed, explicit direction — "each page a different theme and animation, keep that" — after briefly trying a Lissajous-only variant (all four presets as curve-ratio variations) and being told to go back. Don't collapse these back into Lissajous-only variations without being asked again. It must be loaded once per page; do not add a second `id="topographic"` element. The `#topographic` CSS opacity (`.68`) and each preset's internal opacities/reactivity were deliberately turned up because "more prominent/reactive" was requested — don't quietly dial them back down.
- **Animation state must be time-deterministic, not frame-count-dependent.** `puddles`' first implementation tracked "last spawn time" and picked one new ripple per `draw()` call when a real-time interval had elapsed — this silently breaks (renders almost nothing) whenever `requestAnimationFrame` gets throttled (backgrounded/inactive tab, slow device), because each call can only ever advance state by one step no matter how much real time actually passed. The fix, now in place: every ripple's visible state is computed directly as a pure function of the current timestamp (`(time + seed) % life`), so a single `draw()` call always renders the fully-correct instantaneous state regardless of how many frames were skipped to get there. `sound`/`curation`/`cultural` were already written this way by construction (each element's position/opacity is a direct function of `time`, never mutated incrementally frame-over-frame). Apply the same pattern to any future preset or animation on this site.
- Navigation and the site title are hand-authored *inside the HTML templates* in `scripts/build.mjs` (the `header()` function) — not per-page anymore. Update it once there, rebuild, and every page picks up the change.
- **The "Daisy Nduta" logo always links back to the landing page, everywhere it appears as a header** — `.site-title` on every generated page already does this via `header()` (`href="index.html"`; Home itself has no header at all, by design, so there's nothing to link there). `.site-title` also gets `color: #a22106` on hover (`style.css`), matching `.site-nav a:hover`. The admin app's topbar logo (`admin/app.js`, `.topbar__logo`) follows the same rule — it's an `<a href="/" target="_blank">`, opening the live site in a new tab rather than navigating the SPA away (which would lose the current editing session). `publish.html`'s small "Daisy Nduta — Content Manager" text is a plain eyebrow label, not a header/logo in this sense — it doesn't need to become a link.

## Content, the CMS, and the build

**The ~34 `.html` files in the repo root are generated output.** Don't hand-edit them — edit `content/` (directly, or via the local CMS) and run the build. `.build-manifest.json` (gitignored) tracks which item pages the build itself created, so deleting a content file also deletes its stale `.html` output on the next build — don't hand-delete generated `.html` files either, or the manifest and the real file set will disagree.

- **`content/pages/{home,about,contact}.json`** — the three singleton pages, fixed schema. `home.json` additionally carries a top-level `tagline` string (2026-09-20 — see the Home Page tier above).
- **`content/sections/<key>/*.md`** — one Markdown file (YAML frontmatter + a plain-text body paragraph) per credit/project, where `<key>` is one of `film`, `theatre`, `broadcast`, `live`, `studio`, `curation`, `cultural` (matches `TOP_SECTIONS` in `scripts/build.mjs`, which maps each key to its breadcrumb/back-link/`data-bg`). Fields: `title`, `order` (int, controls card position and the prev/next chain — ties break on directory read order), `cardLabel`, `cardSummary`, `details` (list of `{label, value}`), `images` (list of paths under `images/uploads/` — see "Item/Page images are a gallery" below), and the Markdown body (the "Tell us about..." paragraph). `theatre/` deliberately has zero native files today — Kaya/Assimilate live in `cultural/` and guest-appear there via `alsoShowOn`.
- **`alsoShowOn: "<key>"`** (optional) — makes an item's card *also* render on another key's grid (with an auto-generated "X also appears under Y" note on that grid), without duplicating the file. **`crossListedLabel`/`crossListedHref`/`crossListedText`** (optional) — adds the matching "Also listed under..." note on the item's own detail page. Only surfaced in the admin form for the `cultural` collection today (`CROSS_LINK_COLLECTIONS` in `scripts/schema.mjs` — the only place it's currently used); add other collection keys there if another dual-listed project shows up.
- **The client can add whole new top-level pages from the CMS** — a `pages` folder collection (`content/sections/pages/*.md`), distinguished from the other 7 folder collections by `shape: 'page'` in `scripts/schema.mjs` (vs. `shape: 'item'`). Its fields are deliberately narrower than a credit/project item — just `title`, `order`, `images` (see below), and a plain-text `body` (split on blank lines into paragraphs by `paragraphsFromBody()` in `build.mjs`, no cardLabel/cardSummary/details/cross-link fields at all). Each one gets its own generated `<slug>.html` (via `customPageHtml()`) and its own nav link, inserted automatically between Cultural Projects and About, ordered by `order` — `NAV_ITEMS` in `build.mjs` is computed fresh at the top of `build()` from `readFolder('pages')`, not hardcoded, specifically so this works. Titles that would slugify to a core page's own name (`index`/`sound`/`curation-production`/`cultural-projects`/`about`/`contact` — `RESERVED_PAGE_SLUGS` in `schema.mjs`) are rejected by the admin API at creation, and defensively filtered back out again in `build()` in case a reserved slug ever gets into `content/` by hand-editing — don't remove either guard, a same-named page would otherwise silently overwrite one of the six core generated files. The admin form for this collection is `renderPageEntryForm()` in `admin/app.js` (branches off `collection.shape === 'page'` inside `renderItemForm()`), separate from the generic item form.
- **Item/Page images are a gallery, not a single image (2026-09-19, explicit request)** — the 7 credit/project collections and the client-addable `pages` collection all store `images: [<path>, ...]` (an array, possibly empty) instead of a single `image` string. The admin form for both (`imagesFieldHtml()`/`renderImagesList()`/`wireImagesField()` in `admin/app.js`, shared by `renderItemForm()` and `renderPageEntryForm()`) is a repeatable upload widget — thumbnails with a remove (×) each, plus "+ Add image" — backed by `state.currentImages`, since only one form is ever open at a time in this app. On the public detail page, `imageGallery()` in `build.mjs` renders all of an item's images as a plain side-scrolling row (`.image-gallery` in `style.css` — `overflow-x: auto`, fixed-size images, no click-to-swap JS/state) rather than a carousel; zero images still falls back to the same "Image / reel — pending" placeholder as before (empty text for client Pages, which never had a placeholder). Card grids (`.item-card`/`.entry-card`) are unaffected and still only ever show one thumbnail — `itemCard()` in `build.mjs` feeds `mediaBlock()` just the *first* image (`item.images[0]`) as the representative thumbnail. **Home's 5 cards, About's portrait, and Contact stay single-image** — this array-based gallery only applies to the 7 item collections + client Pages, deliberately not extended to those (they're teaser/profile slots, not galleries). If a fresh checkout's content still has the old single `image` field (pre-2026-09-19), it needs the same migration the existing 28 items got: drop `image`, add `images: [<old value>]` or `images: []`.
- **`scripts/build.mjs`** — reads all of the above and writes every `.html` file. Exports `build()` (importable) and also runs standalone via `node scripts/build.mjs` / `npm run build`. All HTML templating (head boilerplate, `.site-header`, card/detail-list/nav markup) lives here now — this is the one place to change shared markup.
- **The admin UI is fully custom** (`admin/index.html` + `admin/app.js` + `admin/style.css`) — **not Decap CMS**. Decap was the first implementation (a proven git-based headless CMS, loaded from unpkg with `local_backend`/`decap-server`) but got replaced after direct feedback that it "still looks very bootstrappy" for the client's daily use, pointing at a cleaner reference tool (`http://127.0.0.1:3000/`, a similar bespoke local-CMS pattern: logo top-left, collections sidebar, entry list + edit form two-pane layout, git-connection status bottom-left, Publish button top-right). If Decap-specific instructions ever resurface (an old `admin/config.yml`, `decap-server` in `package.json`), they're stale — this is a from-scratch vanilla JS single-page app talking to a REST API, no third-party CMS framework, no hashed CSS-in-JS classes to fight.
- **`scripts/schema.mjs`** — the collection registry (`FOLDER_COLLECTIONS`, `FILE_COLLECTIONS`, `CROSS_LINK_COLLECTIONS`, `RESERVED_PAGE_SLUGS`) the admin API, `build.mjs`, and the frontend all read. Each `FOLDER_COLLECTIONS` entry carries a `shape` (`'item'` for the 7 credit/project collections, `'page'` for the client-addable `pages` collection) that both `admin-api.mjs` and `admin/app.js` branch on. Kept deliberately separate from `build.mjs`'s `TOP_SECTIONS` (which carries HTML-specific breadcrumb/backHref/`data-bg` fields, and only covers the 7 `item`-shaped collections, not `pages`) — these must be kept in sync by hand if a collection is added/renamed/removed.
- **`scripts/admin-api.mjs`** — an Express router (mounted at `/api` by `server.mjs`) providing the CRUD surface the frontend calls: `GET/POST/PUT/DELETE /api/collections/:key/entries[/:slug]` for the 7 folder collections (writes/reads Markdown+frontmatter via `gray-matter`), `GET/PUT /api/pages/:key` for the 4 singleton JSON pages (home/about/contact/settings — see "Site-wide highlight color" below), `GET/POST/DELETE /api/media[/:name]` for uploads (via `multer`, into `images/uploads/`), and `GET /api/git-status` (branch, clean/dirty, whether an `origin` remote exists — powers the sidebar's git-connection widget). `POST /api/publish` stays directly in `server.mjs` (pre-existing, unchanged).
- **`admin/app.js`** — the whole frontend: a single vanilla-JS IIFE, no build step or framework, rendering via template-string `innerHTML` (with an `escapeHtml()` helper — don't skip it when adding new fields, this is the one place user-authored text flows back into the DOM). Sidebar lists all 12 collections; `item`-shaped folder collections show a list-of-entries pane + the generic item-edit form (Title/Order/Card Label/Card Summary/Details-list/Image/Description, plus the cross-link fields when `collection.crossLink` is true); the `page`-shaped `pages` collection shares the same list pane but gets the narrower `renderPageEntryForm()` (Title/Order/Image/Body only); the 4 singleton pages each get their own bespoke form function (`renderHomeForm`/`renderAboutForm`/`renderContactForm`/`renderSettingsForm`) since their shapes don't share a generic schema. Deletes go through `confirmDialog()` — an in-page overlay, deliberately **not** the native `confirm()` — because a native dialog blocks the whole tab (including from automated browser control) until a human dismisses it; keep using the custom one for any future destructive action here.
- **The whole admin shell must be rendered inside `#app` staying a flex column (2026-09-19 bug fix).** `admin/index.html` is just `<body><div id="app"></div><script src="app.js"></script></body>`, and `admin/app.js`'s `renderShell()` writes the `.topbar`/`.layout` structure into that div. `admin/style.css`'s scrolling model (`body` a flex column with `overflow:hidden`; `.layout`/`.main`/`.editor` etc. each `flex:` + `overflow-y:auto`) only works if every element in that chain is an actual flex item of a flex parent — and `#app` itself had no CSS at all, making it a plain block box. That silently turned `.topbar`/`.layout`'s `flex`/`min-height` rules into no-ops (they only apply to flex items), so the whole shell grew to its content's full height instead of being capped to the viewport: anything taller than one screen (Home's 5 cards, About's long form) pushed past the bottom of the window with the *document* trying to scroll instead of the intended inner `.editor` pane — and since `body` has `overflow:hidden`, that made the overflow content effectively unreachable ("can't scroll and edit the other cards"). Fixed by giving `#app` its own `flex:1; display:flex; flex-direction:column; min-height:0;` in `admin/style.css`. If the admin shell's markup or CSS is restructured again, keep `#app` (or whatever wraps the rendered shell) part of the same flex chain — this is the one thing easy to silently break again.
- **`server.mjs`** (`npm run cms`) — a single process now (Decap's separate `decap-server` proxy is gone): serves the whole repo root as static files (so the public site, `/admin`, and `/publish.html` are all reachable from one server), mounts the admin API, watches `content/` with `chokidar` and calls `build()` automatically on any change (debounced) — including changes written by the admin API itself, so saving in the UI always triggers a rebuild — and exposes `POST /api/publish`.
- **`publish.html`** — a standalone dashboard (styled to match the main site) with a "Publish to GitHub" button that hits `/api/publish`, which shells out to `git add -A && git commit && git push` in the repo root. Requires a real GitHub remote to actually succeed (`git remote add origin ...`) — setting that up is a one-time step outside this repo's code, not something the CMS does for the client. The same action is also available inline from the admin app's top bar (`handlePublish()` in `admin/app.js`) — keep both wired to the same `/api/publish` endpoint if touching this.
- **Image uploads** land in `images/uploads/` (via the `/api/media` route); `build.mjs` renders `<img src="images/uploads/...">` in place of the text placeholder whenever an item's image(s) are set. Every image-capable field has this wired up: every folder-collection item's `images` gallery (see "Item/Page images are a gallery" below), Home's 5 card images, and About's portrait photo — **Home's card images were a real gap until 2026-09-19**: the `image` field existed in `home.json`'s schema and `build.mjs` already rendered it, but `renderHomeForm()` in `admin/app.js` never actually had the upload UI, so there was no way to set one from the CMS at all until that was added (same upload/preview/remove pattern as everywhere else, just indexed per card since Home's form repeats one block 5 times). Contact intentionally has no image field — the public Contact page has no image slot to fill. Real photography still hasn't been supplied for most items — this only matters once the client starts uploading via the CMS. Removing an image (or all of a gallery's images) in the admin form clears the field (the uploaded file itself stays in `images/uploads/` unless explicitly deleted via `DELETE /api/media/:name`), reverting that card/page back to the placeholder.
- **Uploads are compressed/resized server-side before they ever touch disk**, by explicit request — `scripts/admin-api.mjs`'s `/api/media` POST handler uses `sharp` (memory-storage multer, not disk storage, so the raw upload is never written as-is): longest edge capped at `UPLOAD_MAX_DIMENSION` (2000px, `withoutEnlargement: true` so small images aren't upscaled), re-encoded as JPEG at `UPLOAD_JPEG_QUALITY` (82, `mozjpeg: true`), EXIF orientation applied then stripped. Every non-GIF upload gets normalized to `.jpg` regardless of original format/extension (JPEG/PNG/HEIC/WebP all photos in practice, none need alpha transparency at the sizes this site displays them) — GIFs are the one exception, written through unmodified so animation survives. Typical real-world result: a 3-5MB phone photo becomes ~150-250KB. If the compression target ever needs to change (e.g. the client wants sharper images), adjust the two constants at the top of `admin-api.mjs` rather than the resize/encode calls inline.
- **Every "Upload image" button runs the chosen photo through a pan + zoom crop tool first (2026-09-20, client request: "a way to crop the images")** — `openCropModal(file)` in `admin/app.js`, a plain-JS overlay (same `.confirm-overlay` visual family as `confirmDialog()`) shared by all three upload sites (`wireImagesField()`'s gallery uploader, `renderHomeForm()`'s per-card uploader, `renderAboutForm()`'s portrait uploader). The crop window is a fixed `CROP_VIEWPORT` (480×360, i.e. 4:3, matching `.entry-card__media`/`.item-card__media`) — the photo sits behind it at whatever scale makes it "cover" the window (drag to pan, a range input to zoom in further, both re-clamped so the photo can never leave a gap inside the window). There's deliberately no free-shape corner-resize handle — pan/zoom only, chosen to keep both the math and the UI simple and hard to get into a broken state. "Apply crop" draws the visible region onto a canvas at the source photo's native resolution and uploads that as a Blob (still through the same `/api/media` → sharp pipeline above, so compression is unaffected); "Use original" skips cropping and uploads the file as-is. **GIFs bypass the modal entirely** (`file.type === 'image/gif'` short-circuits to resolving the original `File` immediately) since a canvas re-draw would flatten the animation to one frame — mirrors the server's own `isGif` branch. If this ever needs a genuinely different crop shape per context (e.g. a non-4:3 window for the About portrait slot, which isn't actually 4:3 in `.image-panel`), `CROP_VIEWPORT` would need to become a parameter rather than a shared constant — it's a constant today by deliberate simplification, not an oversight.
- **Site-wide highlight color is client-editable (2026-09-19, explicit request)** — a 4th `FILE_COLLECTIONS` singleton, `content/pages/settings.json` (`{ accentColor: "#a22106" }`), edited from a "Site Settings" admin page (`renderSettingsForm()` in `admin/app.js`: a native `<input type="color">` picker synced with a plain hex text input, plus a "Reset to default" button — deliberately not a free-text field alone, since a bad value would break the highlight color across the whole site). `build.mjs` reads it at the top of `build()`, validates it's a 6-digit hex (`/^#[0-9a-fA-F]{6}$/`, falling back to `DEFAULT_ACCENT_COLOR` in `scripts/schema.mjs` if missing/invalid — a client-entered bad value can't silently break the whole site), and injects it as `<style>:root{--accent:...}</style>` in every page's `<head>` (`head()` in `build.mjs`). `style.css` now uses `var(--accent)` everywhere it used to hardcode `#a22106` (see "Colour" below), with a `:root { --accent: #a22106; }` fallback at the top of the file for anyone opening it directly outside a generated page. `script.js`'s canvas animations read the same custom property at runtime (`getComputedStyle(document.documentElement).getPropertyValue('--accent')`, parsed to an `r, g, b` triplet) rather than hardcoding a separate rgb literal, so the animations' accent-colored elements always match whatever color is actually set — there is deliberately only one source of truth for this color across CSS and canvas. Admin's own UI (buttons, active sidebar item, etc. in `admin/style.css`) stays hardcoded to `#a22106` — that's the existing "asymmetry is intentional" CMS-vs-public-site split (see "Colour" below), not wired to the client's chosen color.

## Commands

```sh
npm install       # one-time
npm run build      # content/ -> the static .html files, once
npm run cms        # runs server.mjs (single process); edit at http://localhost:8080/admin/,
                    # preview at http://localhost:8080/, publish at http://localhost:8080/publish.html

# Quick read-only static preview without the CMS (no editing, no auto-rebuild):
python3 -m http.server 8000

node --check script.js   # syntax-check the shared client-side JS
```

Hosting is GitHub Pages at the custom domain `daisynduta.com` (confirmed, `CNAME` committed to the repo root). Do not host a live preview yourself or generate/fetch new images — real photography comes from the client via the CMS's image upload, once supplied.

**Non-technical entry point (2026-09-19, explicit request):** `First-Time Setup.command`/`.app` and `Start Content Manager.command`/`.app` at the repo root let Daisy run all of the above without opening a terminal or knowing any commands. The `.command` files are the actual logic (plain shell scripts, double-clickable on macOS, run via Terminal): `First-Time Setup` installs Node.js if missing (via Homebrew if present, otherwise opens the official nodejs.org installer page and waits) then runs `npm install` then hands off into `Start Content Manager`, which runs `npm run cms` and opens the site preview + `/admin/` in the browser automatically. The `.app` bundles are thin GUI wrappers around those same `.command` files (`Contents/MacOS/launcher` just does `open -a Terminal ".../X.command"`), which exist purely so Finder shows a real app icon/name instead of the generic terminal-script icon — they must stay next to their matching `.command` file (they resolve it via a relative path, `$(dirname "$0")/../../..`) and aren't meaningful moved elsewhere on their own. The icon (`AppIcon.icns` inside each bundle) is a generated DN monogram matching `images/favicon.ico`'s "D in ink, N in accent" treatment — regenerate via Pillow + macOS `iconutil` if it ever needs to change, there's no source file checked in beyond the compiled `.icns`. README.md's client-facing instructions point at the `.app` versions; keep both in sync if either changes.

## Visual system: preserve unless explicitly asked to change

- **Colour:** white/black base — body `#fff`, primary text `#201e1f`, everything else is `rgba(32, 30, 31, X)` opacity steps of that same near-black (the old pale-peach `#fff0e7` accent from the template era is gone) — **plus a rust accent (`#a22106` by default), used only as a highlight on interactive/hover states**, by explicit request: `.site-nav a:hover`/`[aria-current="page"]`, `.entry-card`/`.item-card` hover (border + arrow icon color), `.placeholder` link hover. It is not a base fill color anywhere on the public site — don't repaint large areas or default states with it, it's specifically a highlight. **The exact color is client-editable (2026-09-19)** via a `--accent` CSS custom property rather than a hardcoded hex — see "Site-wide highlight color is client-editable" above for the full mechanism (Site Settings admin page → `content/pages/settings.json` → injected per-page → `style.css`'s `var(--accent)` + `script.js`'s canvas animations both read it). Treat `#a22106` below and throughout this doc as "the default value of `--accent`," not a hardcoded constant — the actual rendered color on a live site may differ if the client has changed it. It's also used as a typographic accent on select words within the three fixed `hero-lede` headline sentences (`.accent` span in `style.css`, applied by hand in `scripts/build.mjs` — "Sound design" on Sound, "live experiences" on Curation & Production, "community-rooted" on Cultural Projects), one phrase per headline, not more — this only applies to those hardcoded template sentences, not to CMS-editable heading text (About/Contact headings, item titles), since injecting `<span>` markup into a plain-text field the client edits via the admin form would silently get stripped/escaped and is fragile to begin with. **Card titles also get it, automatically:** `accentLastWord()` in `scripts/build.mjs` wraps the last word of any card title with 2+ words in `.accent` — applied to every `.entry-card h2` (Home) and `.item-card h3` (section grids); single-word titles ("Nightjar", "MPavilion", "Sound") are deliberately left plain, which is what gives the effect its "some, not all" variety — don't try to force an accent onto single-word titles. This is a static, generated-at-build-time rule (part of "bake them in" — explicitly not a CMS-configurable field), so it applies uniformly to every card without per-item exceptions. - **Home's rotating cards (2026-09-17, iterated across several follow-ups the same day):** client asked for the 5 entry cards to rotate rather than sit in a static grid, referencing another site's full 3D card carousel (Three.js/WebGL) as inspiration. Went through a **rigid rotating-cylinder architecture first, which was abandoned as fundamentally the wrong shape for this** — worth understanding why, since it's a real trap if this gets touched again.
  - **Current architecture** (all in the guarded IIFE at the bottom of `script.js`, inert on every page but Home; markup is just `.entry-carousel > .entry-carousel__track > 5x .entry-card` + `.entry-carousel__controls`, generated in `build.mjs`'s `index.html` section): there is no persistent rotation state and no rotating parent element. Every card's full `transform` is recomputed from scratch on every `render()` call, purely as a function of its own bounded `delta` (its shortest signed distance, `-2..2` for 5 cards, from whichever card is currently active): `translateX(-50% + delta*HORIZONTAL_STEP%) translateY(delta*VERTICAL_STEP) rotateY(delta*FAN_ANGLE) translateZ(-|delta|*DEPTH_STEP) scale(SCALE_STEP[|delta|])`. `FAN_ANGLE` (`26deg`) is deliberately shallow — shallow enough that even `|delta|=2` stays inside the front-facing hemisphere, so up to 4 of the 5 cards can be visible and legible at once, fanned out like a hand of cards. `HORIZONTAL_STEP` (in `%`, currently `115`) is what actually keeps them from overlapping — rotateY+translateZ alone only shift a card sideways as a *weak side effect* of foreshortening (proportional to `sin(angle)*depth`), nowhere near enough spread for ~560px-wide cards, so there's an explicit horizontal offset doing the real work. `SCALE_STEP` (`[1, .78, .6]`, indexed by `|delta|`) is a second, independent lever on top of that — every card shares the same layout width regardless of `delta`, so this explicitly shrinks peeking cards' real bounding box rather than relying on perspective foreshortening alone. Current values for all four (`FAN_ANGLE=26`, `DEPTH_STEP=260`, `HORIZONTAL_STEP=115`, `VERTICAL_STEP=58`) are the result of several rounds of live-verified tuning below — treat them as the known-good baseline, not a starting guess.
  - **Why there's no rotating ring anymore:** the first version had a `.stage > .ring > 5 cards` structure where the *ring* physically rotated (`rotateY(-active*angleStep)`) to sweep fixed cards past the front, forming a true rigid cylinder. That only self-consistently "recycles" — i.e. correctly identifies which card is at the front — if `angleStep` is exactly `360/total` (72deg for 5 cards). The client then asked for a shallower angle so more cards would be visible (the 72deg version only ever showed a sliver of each immediate neighbor and read as "amateurish"), and a shallower angle silently breaks that assumption: logged the actual net angles per step and confirmed that once `active` ran past `total-1`, the card labeled "active" (via `delta===0`) was nowhere near 0deg (e.g. sitting at -170deg) — the ring kept spinning correctly, but which physical card was "at the front" drifted out of sync with which one the code *thought* was at the front. That's a hard geometric constraint of a rigid rotating cylinder with a fixed small card count, not a bug to patch — hence dropping the ring entirely in favor of recomputing every card's position fresh each render from a bounded `delta`, which has no such constraint and works at any `FAN_ANGLE`.
  - **The one thing a delta-based (non-rigid) design has to handle explicitly: the wraparound "jump."** Every `next()`/`prev()` shifts every card's `delta` by exactly 1 — except the one card at the extreme edge (`delta===2` going further, or `delta===-2`), which necessarily jumps straight to the opposite extreme (`2 → -2` or the reverse) every single step. Animating that jump with the normal CSS transition would visibly swing that card back across the front. `render()` detects this per-card (`Math.abs(delta - prevDelta[i]) > 1`), sets `transition: none` for that one card for a single frame (forcing a reflow via `card.offsetWidth` so the browser actually applies the "no transition" before the new transform, then restoring the real transition on the next animation frame), so that specific card *pops* instantly into its new spot instead of animating across the scene. It's always the dimmest, furthest-out card when this happens, so the pop reads as basically invisible in practice — confirmed by scripting 8 rapid `next()` calls and checking that exactly one card has `transition:'none'` on every step, in a consistent rotating pattern.
  - **The spin is still endless and never resets**, same underlying fix as before: `active` (the step counter) is *never* wrapped — `next()`/`prev()` just do `active += 1` / `active -= 1` forever. Only the per-card `delta` used for rendering is bounded, recomputed fresh every call via `(i - active) % total` normalized into the minimal range — so it can't drift no matter how many steps have happened, and there's no persisted rotation value to ever need clamping/resetting. `goTo(index)` (dots, or clicking a visible-but-not-front card) still needs to land on a specific logical index — it computes the shortest-path *adjustment* to the unbounded `active` rather than assigning it directly, so a direct jump takes the short way around.
  - Opacity by distance from front: `1` / `.85` / `.5` / `0` for `|delta|` = 0/1/2/3+ — with only 5 cards and `|delta|` maxing at 2, the `0` case never actually fires today, it's just a defensive fallback. `backface-visibility: hidden` is kept for the same reason, even though `FAN_ANGLE=26` never gets close to the 90deg it guards against.
  - **Only the active card shows its text (2026-09-18):** with up to 4 cards fanned out at once, their `.entry-card__body` (label/title/summary) and `.entry-card__arrow` all sat in roughly the same lower band and piled into unreadable overlapping text — "the cards are overlapping and looking really bad." Two separate input paths, since they arrive as different DOM events: **touch** (`touchstart`/`touchend` on `.entry-carousel`, `SWIPE_THRESHOLD = 40px`, only acts when the horizontal delta clearly exceeds the vertical one, so scrolling the page through the carousel on a phone isn't swallowed as a card change) and **trackpad** (`wheel` events with a dominant `deltaX` — a two-finger trackpad swipe reports this way, it is *not* a touch event even on a touchscreen laptop). Setup, for reference if this ever needs redoing (e.g. rotating the key, or setting up a fresh checkout): a passwordless ed25519 keypair lives at `.deploy/github_deploy_key`(`.pub`) — **gitignored, never committed**, since the private key grants write access to the repo — added to GitHub via `gh repo deploy-key add .deploy/github_deploy_key.pub --repo Daisy-Nduta/daisy-nduta-website --allow-write`; `origin` is set to the SSH form (`git@github.com:Daisy-Nduta/daisy-nduta-website.git`); and this repo's *local* git config (`core.sshCommand`, stored in `.git/config`, never committed) points at that key specifically (`-o IdentitiesOnly=yes` so it can't accidentally fall back to some other key/account on the machine). Because the key file and the git config are both outside version control, they only exist on a machine that already has them — copying/AirDropping the whole project folder (including `.deploy/`) to Daisy's computer carries the working setup with it; a fresh `git clone` elsewhere would need this whole dance repeated (or the key file copied over and `core.sshCommand`/`origin` reconfigured). Revoke/rotate by deleting the deploy key from the repo's GitHub settings (or `gh repo deploy-key delete`) and generating a new pair — nothing else on the client's end needs to change since the CMS only ever calls plain `git push`, agnostic to how it authenticates.
