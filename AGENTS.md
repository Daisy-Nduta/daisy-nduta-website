# AGENTS.md

## Scope and architecture

This is **Daisy Nduta**'s (Nairobi-based sound designer, location recordist, and cultural producer) portfolio site: static HTML/CSS/JS, hosted on **GitHub Pages** (free tier) with a custom domain the client points at it. As of the CMS work, the site has a build step — **read "Content, the CMS, and the build" below before touching any `.html` file.**

- Content/IA source of truth for wording: `daisy-nduta-website-copy.md.pdf` in the project root (client-supplied copy doc). Treat its wording, tables, and the "Open items still needed from you" list as authoritative; do not invent facts to fill gaps it leaves open. The PDF's actual data now lives in `content/`, not embedded in HTML — see below.
- Three tiers of page, all sharing `style.css` and deferred `script.js`:
  1. **Home** (`index.html`) — no header/nav at all. A giant centered `h1.home-wordmark` ("Daisy Nduta") sits on top of five large `.entry-card` links (Sound / Curation & Production / Cultural Projects / About / Contact) — the whole journey starts from these cards, no nav needed. `.page--home` carries extra top margin so the wordmark has real breathing room below the header-less top of the page.
  2. **Section pages** — `sound.html`, `curation-production.html`, `cultural-projects.html`, `about.html`, `contact.html`. These keep the persistent top-right `.site-header`/`.site-nav` (a left-hand rail nav was tried and reverted — see below). Sound has five `.section`s (Film, Theatre, Broadcast, Live, Studio, each with an `id` used as an anchor target, e.g. `sound.html#film`), each listing its credits as an `.item-grid` of `.item-card`s. Curation & Production and Cultural Projects are a single `.item-grid` each.
  3. **Item detail pages** — one HTML file per credit/project (~28 files, e.g. `mwakenya.html`, `kilele-summit.html`, `frequency-shift.html`). Each has a breadcrumb eyebrow, title, `.image-panel` (placeholder or a real `<img>` once one's uploaded), copy paragraph, a `.detail-list` of role/year/credit facts, and a `.project-navigation` (back-to-section link + prev/next within that subsection, looping).
- **Navigation history:** a left-hand fixed rail (`.site-rail`, small ~13px vertical links) replaced the top nav briefly, then was reverted back to the original top-right `.site-header`/`.site-nav` because it "wasn't looking the best." If asked to revisit nav placement, treat the current top-right layout as the known-good baseline, not the rail.
- **Kaya** and **Assimilate** are genuinely the same two projects in both Sound → Theatre and Cultural Projects (per the PDF's own cross-reference note) — they exist as a single `kaya.html`/`assimilate.html` file each (and a single content file each, under `content/sections/cultural/`), with a `.cross-listed` note pointing to the other section, rather than being duplicated. Their prev/next chain runs through Cultural Projects (frequency-shift → mau-from-nowhere → kaya → assimilate), since that's their fuller framing in the PDF; Sound → Theatre's card grid *also* shows their cards via the `alsoShowOn` content field (see below). Every other "mau from nowhere" credit (the Film music-video Producer credit, the Curation & Production listening party, and the Cultural Projects artist-management entry) is a genuinely distinct engagement with its own content file — don't merge those.
- `script.js` creates `#topographic` itself and draws one of **four genuinely different pointer-reactive animations**, chosen per page via `<body data-bg="...">` (no attribute — Home/About/Contact — falls back to `puddles`): `puddles` (a single shared water surface — a stack of horizontal lines whose displacement at every point is the *sum* of every ripple source's wave, so overlapping ripples reinforce or cancel each other rather than existing as independent circles; most sources trail the pointer), `sound` (Sound section + its item pages; a stack of flowing waveform lines that swell in amplitude near the pointer), `curation` (Curation & Production + its items; a large orbital/planetary system — 6 elliptical orbit rings extending well past the viewport, a central body, and planets that speed up, glow, and leave a short trailing echo along their orbit as the pointer passes near them), `cultural` (Cultural Projects + its items, including the shared Kaya/Assimilate pages; a drifting node network where the pointer itself joins as a node). This is the confirmed, explicit direction — "each page a different theme and animation, keep that" — after briefly trying a Lissajous-only variant (all four presets as curve-ratio variations) and being told to go back. Don't collapse these back into Lissajous-only variations without being asked again. It must be loaded once per page; do not add a second `id="topographic"` element. The `#topographic` CSS opacity (`.68`) and each preset's internal opacities/reactivity were deliberately turned up because "more prominent/reactive" was requested — don't quietly dial them back down.
- **Animation state must be time-deterministic, not frame-count-dependent.** `puddles`' first implementation tracked "last spawn time" and picked one new ripple per `draw()` call when a real-time interval had elapsed — this silently breaks (renders almost nothing) whenever `requestAnimationFrame` gets throttled (backgrounded/inactive tab, slow device), because each call can only ever advance state by one step no matter how much real time actually passed. The fix, now in place: every ripple's visible state is computed directly as a pure function of the current timestamp (`(time + seed) % life`), so a single `draw()` call always renders the fully-correct instantaneous state regardless of how many frames were skipped to get there. `sound`/`curation`/`cultural` were already written this way by construction (each element's position/opacity is a direct function of `time`, never mutated incrementally frame-over-frame). Apply the same pattern to any future preset or animation on this site.
- Navigation and the site title are hand-authored *inside the HTML templates* in `scripts/build.mjs` (the `header()` function) — not per-page anymore. Update it once there, rebuild, and every page picks up the change.
- **The "Daisy Nduta" logo always links back to the landing page, everywhere it appears as a header** — `.site-title` on every generated page already does this via `header()` (`href="index.html"`; Home itself has no header at all, by design, so there's nothing to link there). `.site-title` also gets `color: #a22106` on hover (`style.css`), matching `.site-nav a:hover`. The admin app's topbar logo (`admin/app.js`, `.topbar__logo`) follows the same rule — it's an `<a href="/" target="_blank">`, opening the live site in a new tab rather than navigating the SPA away (which would lose the current editing session). `publish.html`'s small "Daisy Nduta — Content Manager" text is a plain eyebrow label, not a header/logo in this sense — it doesn't need to become a link.

## Content, the CMS, and the build

**The ~34 `.html` files in the repo root are generated output.** Don't hand-edit them — edit `content/` (directly, or via the local CMS) and run the build. `.build-manifest.json` (gitignored) tracks which item pages the build itself created, so deleting a content file also deletes its stale `.html` output on the next build — don't hand-delete generated `.html` files either, or the manifest and the real file set will disagree.

- **`content/pages/{home,about,contact}.json`** — the three singleton pages, fixed schema.
- **`content/sections/<key>/*.md`** — one Markdown file (YAML frontmatter + a plain-text body paragraph) per credit/project, where `<key>` is one of `film`, `theatre`, `broadcast`, `live`, `studio`, `curation`, `cultural` (matches `TOP_SECTIONS` in `scripts/build.mjs`, which maps each key to its breadcrumb/back-link/`data-bg`). Fields: `title`, `order` (int, controls card position and the prev/next chain — ties break on directory read order), `cardLabel`, `cardSummary`, `details` (list of `{label, value}`), `image` (optional, path under `images/uploads/`), and the Markdown body (the "Tell us about..." paragraph). `theatre/` deliberately has zero native files today — Kaya/Assimilate live in `cultural/` and guest-appear there via `alsoShowOn`.
- **`alsoShowOn: "<key>"`** (optional) — makes an item's card *also* render on another key's grid (with an auto-generated "X also appears under Y" note on that grid), without duplicating the file. **`crossListedLabel`/`crossListedHref`/`crossListedText`** (optional) — adds the matching "Also listed under..." note on the item's own detail page. Only surfaced in the admin form for the `cultural` collection today (`CROSS_LINK_COLLECTIONS` in `scripts/schema.mjs` — the only place it's currently used); add other collection keys there if another dual-listed project shows up.
- **The client can add whole new top-level pages from the CMS** — a `pages` folder collection (`content/sections/pages/*.md`), distinguished from the other 7 folder collections by `shape: 'page'` in `scripts/schema.mjs` (vs. `shape: 'item'`). Its fields are deliberately narrower than a credit/project item — just `title`, `order`, optional `image`, and a plain-text `body` (split on blank lines into paragraphs by `paragraphsFromBody()` in `build.mjs`, no cardLabel/cardSummary/details/cross-link fields at all). Each one gets its own generated `<slug>.html` (via `customPageHtml()`) and its own nav link, inserted automatically between Cultural Projects and About, ordered by `order` — `NAV_ITEMS` in `build.mjs` is computed fresh at the top of `build()` from `readFolder('pages')`, not hardcoded, specifically so this works. Titles that would slugify to a core page's own name (`index`/`sound`/`curation-production`/`cultural-projects`/`about`/`contact` — `RESERVED_PAGE_SLUGS` in `schema.mjs`) are rejected by the admin API at creation, and defensively filtered back out again in `build()` in case a reserved slug ever gets into `content/` by hand-editing — don't remove either guard, a same-named page would otherwise silently overwrite one of the six core generated files. The admin form for this collection is `renderPageEntryForm()` in `admin/app.js` (branches off `collection.shape === 'page'` inside `renderItemForm()`), separate from the generic item form.
- **`scripts/build.mjs`** — reads all of the above and writes every `.html` file. Exports `build()` (importable) and also runs standalone via `node scripts/build.mjs` / `npm run build`. All HTML templating (head boilerplate, `.site-header`, card/detail-list/nav markup) lives here now — this is the one place to change shared markup.
- **The admin UI is fully custom** (`admin/index.html` + `admin/app.js` + `admin/style.css`) — **not Decap CMS**. Decap was the first implementation (a proven git-based headless CMS, loaded from unpkg with `local_backend`/`decap-server`) but got replaced after direct feedback that it "still looks very bootstrappy" for the client's daily use, pointing at a cleaner reference tool (`http://127.0.0.1:3000/`, a similar bespoke local-CMS pattern: logo top-left, collections sidebar, entry list + edit form two-pane layout, git-connection status bottom-left, Publish button top-right). If Decap-specific instructions ever resurface (an old `admin/config.yml`, `decap-server` in `package.json`), they're stale — this is a from-scratch vanilla JS single-page app talking to a REST API, no third-party CMS framework, no hashed CSS-in-JS classes to fight.
- **`scripts/schema.mjs`** — the collection registry (`FOLDER_COLLECTIONS`, `FILE_COLLECTIONS`, `CROSS_LINK_COLLECTIONS`, `RESERVED_PAGE_SLUGS`) the admin API, `build.mjs`, and the frontend all read. Each `FOLDER_COLLECTIONS` entry carries a `shape` (`'item'` for the 7 credit/project collections, `'page'` for the client-addable `pages` collection) that both `admin-api.mjs` and `admin/app.js` branch on. Kept deliberately separate from `build.mjs`'s `TOP_SECTIONS` (which carries HTML-specific breadcrumb/backHref/`data-bg` fields, and only covers the 7 `item`-shaped collections, not `pages`) — these must be kept in sync by hand if a collection is added/renamed/removed.
- **`scripts/admin-api.mjs`** — an Express router (mounted at `/api` by `server.mjs`) providing the CRUD surface the frontend calls: `GET/POST/PUT/DELETE /api/collections/:key/entries[/:slug]` for the 7 folder collections (writes/reads Markdown+frontmatter via `gray-matter`), `GET/PUT /api/pages/:key` for the 3 singleton JSON pages, `GET/POST/DELETE /api/media[/:name]` for uploads (via `multer`, into `images/uploads/`), and `GET /api/git-status` (branch, clean/dirty, whether an `origin` remote exists — powers the sidebar's git-connection widget). `POST /api/publish` stays directly in `server.mjs` (pre-existing, unchanged).
- **`admin/app.js`** — the whole frontend: a single vanilla-JS IIFE, no build step or framework, rendering via template-string `innerHTML` (with an `escapeHtml()` helper — don't skip it when adding new fields, this is the one place user-authored text flows back into the DOM). Sidebar lists all 11 collections; `item`-shaped folder collections show a list-of-entries pane + the generic item-edit form (Title/Order/Card Label/Card Summary/Details-list/Image/Description, plus the cross-link fields when `collection.crossLink` is true); the `page`-shaped `pages` collection shares the same list pane but gets the narrower `renderPageEntryForm()` (Title/Order/Image/Body only); the 3 singleton pages each get their own bespoke form function (`renderHomeForm`/`renderAboutForm`/`renderContactForm`) since their shapes don't share a generic schema. Deletes go through `confirmDialog()` — an in-page overlay, deliberately **not** the native `confirm()` — because a native dialog blocks the whole tab (including from automated browser control) until a human dismisses it; keep using the custom one for any future destructive action here.
- **`server.mjs`** (`npm run cms`) — a single process now (Decap's separate `decap-server` proxy is gone): serves the whole repo root as static files (so the public site, `/admin`, and `/publish.html` are all reachable from one server), mounts the admin API, watches `content/` with `chokidar` and calls `build()` automatically on any change (debounced) — including changes written by the admin API itself, so saving in the UI always triggers a rebuild — and exposes `POST /api/publish`.
- **`publish.html`** — a standalone dashboard (styled to match the main site) with a "Publish to GitHub" button that hits `/api/publish`, which shells out to `git add -A && git commit && git push` in the repo root. Requires a real GitHub remote to actually succeed (`git remote add origin ...`) — setting that up is a one-time step outside this repo's code, not something the CMS does for the client. The same action is also available inline from the admin app's top bar (`handlePublish()` in `admin/app.js`) — keep both wired to the same `/api/publish` endpoint if touching this.
- **Image uploads** land in `images/uploads/` (via the `/api/media` route); `build.mjs` renders `<img src="images/uploads/...">` in place of the text placeholder whenever an item's `image` field is set. Every image-capable field already has this wired up: every folder-collection item's `Image` field, Home's 5 card images, and About's portrait photo. Contact intentionally has no image field — the public Contact page has no image slot to fill. Real photography still hasn't been supplied for most items — this only matters once the client starts uploading via the CMS. Removing an image in the admin form clears the field (the uploaded file itself stays in `images/uploads/` unless explicitly deleted via `DELETE /api/media/:name`), reverting that card/page back to the placeholder.
- **Uploads are compressed/resized server-side before they ever touch disk**, by explicit request — `scripts/admin-api.mjs`'s `/api/media` POST handler uses `sharp` (memory-storage multer, not disk storage, so the raw upload is never written as-is): longest edge capped at `UPLOAD_MAX_DIMENSION` (2000px, `withoutEnlargement: true` so small images aren't upscaled), re-encoded as JPEG at `UPLOAD_JPEG_QUALITY` (82, `mozjpeg: true`), EXIF orientation applied then stripped. Every non-GIF upload gets normalized to `.jpg` regardless of original format/extension (JPEG/PNG/HEIC/WebP all photos in practice, none need alpha transparency at the sizes this site displays them) — GIFs are the one exception, written through unmodified so animation survives. Typical real-world result: a 3-5MB phone photo becomes ~150-250KB. If the compression target ever needs to change (e.g. the client wants sharper images), adjust the two constants at the top of `admin-api.mjs` rather than the resize/encode calls inline.

## Commands

```sh
npm install       # one-time
npm run build      # content/ -> the static .html files, once
npm run cms        # runs server.mjs (single process); edit at http://localhost:8080/admin/,
                    # preview at http://localhost:8080/, publish at http://localhost:8080/publish.html

# Quick read-only static preview without the CMS (no editing, no auto-rebuild):
python3 -m http.server 8000

node --check script.js   # syntax-check the shared client-side JS
```

Hosting is GitHub Pages; the custom domain is configured client-side via GitHub's own Pages settings (not part of this repo beyond an eventual `CNAME` file, if/when the domain is confirmed). Do not host a live preview yourself or generate/fetch new images — real photography comes from the client via the CMS's image upload, once supplied.

## Visual system: preserve unless explicitly asked to change

- **Colour:** white/black base — body `#fff`, primary text `#201e1f`, everything else is `rgba(32, 30, 31, X)` opacity steps of that same near-black (the old pale-peach `#fff0e7` accent from the template era is gone) — **plus a `#a22106` rust accent, used only as a highlight on interactive/hover states**, by explicit request: `.site-nav a:hover`/`[aria-current="page"]`, `.entry-card`/`.item-card` hover (border + arrow icon color), `.placeholder` link hover. It is not a base fill color anywhere on the public site — don't repaint large areas or default states with it, it's specifically a highlight. It's also used as a typographic accent on select words within the three fixed `hero-lede` headline sentences (`.accent` span in `style.css`, applied by hand in `scripts/build.mjs` — "Sound design" on Sound, "live experiences" on Curation & Production, "community-rooted" on Cultural Projects), one phrase per headline, not more — this only applies to those hardcoded template sentences, not to CMS-editable heading text (About/Contact headings, item titles), since injecting `<span>` markup into a plain-text field the client edits via the admin form would silently get stripped/escaped and is fragile to begin with. **Card titles also get it, automatically:** `accentLastWord()` in `scripts/build.mjs` wraps the last word of any card title with 2+ words in `.accent` — applied to every `.entry-card h2` (Home) and `.item-card h3` (section grids); single-word titles ("Nightjar", "MPavilion", "Sound") are deliberately left plain, which is what gives the effect its "some, not all" variety — don't try to force an accent onto single-word titles. This is a static, generated-at-build-time rule (part of "bake them in" — explicitly not a CMS-configurable field), so it applies uniformly to every card without per-item exceptions. Detail-page `h1` titles do **not** get this treatment, only card titles — scope it there if extending further. The admin UI (see "Content, the CMS, and the build") uses the same accent much more heavily, on primary actions (New entry, Save/Create, Publish, active sidebar item) — that asymmetry (subtle on the public site, prominent in the CMS) is intentional, not an inconsistency to "fix." `admin/index.html`'s banner and `publish.html` also follow the site's Anton/Futura type system, by the same explicit request that the CMS "follow the same style as the website."
- **Select phrases within body copy get it too, via the same "compute at build time, don't store markup" approach as card titles** — `applyAccents(rawText, phrases)` in `scripts/build.mjs` takes plain text and a hand-picked phrase list, and wraps only the *first* occurrence of each phrase (so a repeated word like "Film" doesn't light up every time it appears — e.g. in About's third paragraph, only the practice-area mention gets it, not the later "Melbourne International Film Festival"). Currently applied to About's 4 bio paragraphs via `ABOUT_PARAGRAPH_ACCENTS` (a parallel array, one phrase list per paragraph index — `['sound-first']`, `['cultural producer']`, `['Sound', 'Film', 'Curation & Production', 'Cultural Projects']` — the third paragraph's four phrases are literally the site's four section names, tying the bio straight back to the nav — and `[]` for the fourth paragraph, since not every paragraph needs one). The phrase list lives in code, not in `content/pages/about.json` — the stored paragraph text stays plain, so the CMS textarea shows clean editable prose, not raw HTML. If the client edits a paragraph's wording through the admin app, the accent phrase may stop matching (silently, no error) if the exact phrase no longer appears — that's an acceptable, low-stakes failure mode (worst case: one paragraph loses its highlight), not worth adding validation for. Extend `ABOUT_PARAGRAPH_ACCENTS` or add the same pattern to another page's copy (e.g. Contact's intro) if asked; keep it sparse — one or a small cluster of phrases per paragraph, not a phrase in every sentence.
- **Every `.section h2` subheading gets the *entire* heading accented** (`accentFull()` in `scripts/build.mjs`, distinct from `accentLastWord()`) — Sound's 5 subsection headers (Film/Theatre/Broadcast/Live/Studio, hardcoded via `SOUND_SUBSECTIONS`), and About/Contact's CMS-editable subheadings (Awards/Residencies & Programs/Trusted by/Contact details, via the same "compute at render time from plain `content/` text" approach as the phrase-highlighted paragraphs — the stored heading text stays plain in `content/pages/{about,contact}.json`). This was an explicit follow-up ("still sparse... add it to subheadings across the pages") after the phrase-based approach felt too sparse on its own — unlike `accentLastWord`/`applyAccents`, there's no partial-match logic here, the whole subheading is always accent-colored, full stop. Curation & Production and Cultural Projects have no `.section h2` (they go straight from the `h1` to the card grid) — nothing to accent there.
- **Three of the four background animations carry the accent, sparingly** — each one's single most pointer-reactive element, everything else stays in the near-black `INK` palette: `sound`'s one "lead" waveform line (index 3 of 7), `curation`'s central body plus the glow/trailing-echo effect that appears when the pointer nears a planet, `cultural`'s pointer's own node and its connection lines. `script.js` defines `ACCENT = 'rgba(162, 33, 6,'` alongside the existing `INK` constant for this. `puddles` briefly had pointer-linked ripple sources drawing a visible expanding accent ring plus a filled center dot (added because the preset's accent read as "missing" next to the other three) but that was removed on explicit follow-up feedback — "quite distracting" — so `puddles` is currently accent-free, INK-only. Don't re-add a mouse-following marker there without being asked; if `puddles` needs an accent touch again, prefer tinting the water lines themselves (reinforcing existing interference) over a shape that visibly tracks the cursor.
- `puddles`' line density (`WATER_LINES` in `script.js`, currently `46`) was doubled from the original `24` on explicit request ("many and closer") — the Home/About/Contact background should read as a dense woven surface, not sparse ruled lines. `WATER_POINTS` (samples per line, `200`) controls smoothness along each line, not density between lines — don't conflate the two if tuning this again.
- **Type:** Anton (Google Fonts) for headlines, nav, logo, and card/item titles (`h1`, `h2`, `h3`, `.site-title`, `.site-nav a`, `.detail-list span:first-child`). Futura for body copy — `font-family: "Futura", "Futura PT", "Century Gothic", sans-serif` on `body`. Futura isn't a free hosted webfont (it's Monotype-licensed), so this relies on the visitor's system having it installed (common on Mac); everyone else sees the "Century Gothic"/sans-serif fallback. If a licensed Futura webfont file is ever supplied, wire it in via `@font-face` instead of the system-font stack.
- **Header:** 52px/32px desktop padding, plain-text `.site-title` ("Daisy Nduta", not an image — `images/logo.png` is a leftover unused Frequency Shift wordmark), large (38px desktop) and left-aligned. `.site-nav` sits at the top-right, small (13px) and tightly grouped — deliberately quiet relative to the logo, not the earlier 26px version. Home's header is absent entirely (see `.home-wordmark` below), not even the logo. Mobile breakpoint is 700px.
- **Cards:** `.entry-card` (Home, 5 of them, large with a 4:3 image slot, the 5th spans full width at 21:9) and `.item-card` (section-page grids, smaller, 3-up desktop) both use white fill, `rgba(32,30,31,.15)` border, 12px radius, and an `rgba(32,30,31,.04)` placeholder-image block.
- **Long headline copy:** apply the `h1.hero-lede` modifier (smaller clamp, tighter line-height) to any h1 carrying a full sentence rather than a short punchy title. Short titles (About, Contact, item-detail pages) use the base `h1` styling.

## Implementation cautions

- Don't hand-edit generated `.html` files — see "Content, the CMS, and the build" above. Shared markup (header, footer, card templates) lives in `scripts/build.mjs`; per-item content lives in `content/`.
- Preserve `aria-current="page"`, relative URLs, section anchor `id`s (`#film`, `#theatre`, etc.), and the `alt`/`aria-label` text already in place.
- The PDF flags several unresolved content questions (Binti's release year, whether Legacy/Chops & Drops need a separate "TV" subsection, release-status wording for Nightjar and the mau from nowhere music video). These are intentionally left as inline placeholder notes/content values — do not silently resolve them one way or the other without the client's answer.
- No GitHub remote is configured in this repo yet — `publish.html`'s Publish button will fail at the `git push` step until one is (`git remote add origin <url>`), which needs the client's or an explicitly-confirmed decision, not something to set up unilaterally.
